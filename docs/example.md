# Worked Example: A Fictional Candidate and Staff Engineer Role

This example is illustrative. The candidate, company details, and experience are fictional.

## Candidate starting point

Jordan has 12 years of financial-services experience:
- 7 years building backend systems.
- 3 years leading technical delivery across teams.
- 2 years working with AWS services.
- Experience with Java, Kafka, Kubernetes, and relational databases.
- A personal scheduling application built outside work.

Jordan's existing resume is two pages and mostly lists technologies and responsibilities.

## Stage 1: Interview

Follow-up questions reveal:
- The project replaced point-to-point integrations with event-driven messaging.
- Jordan implemented two consumers and supported production troubleshooting.
- A platform team owned Kafka infrastructure.
- Jordan coordinated schema changes with four downstream teams.
- The project reduced manual reconciliation, but no verified percentage exists.

## Stage 2: Inventory

**Problem:** Multiple applications received inconsistent transaction updates.

**Contribution:** Implemented two Kafka consumers, coordinated schema compatibility with four downstream teams, and supported production troubleshooting.

**Boundaries:** Platform engineering owned Kafka cluster operations; Jordan did not administer the brokers.

**Outcome:** Reduced manual reconciliation work. Exact time or cost savings were not measured.

**Evidence status:** Consumer count and downstream-team count were confirmed by Jordan; savings remain qualitative.

## Stage 3: Evaluate a hypothetical role

A fictional fintech company posts a Staff Backend Engineer role asking for distributed systems design, AWS production experience, cross-team technical influence, and Java or Go. Formal management experience is not required.

| Requirement | Assessment | Evidence |
|---|---|---|
| Distributed systems | Direct | Kafka consumers and event integration |
| AWS | Partial | Two years of AWS delivery; validate service depth |
| Cross-team influence | Direct | Schema compatibility across four teams |
| Java or Go | Partial | Java hands-on; Go requires confirmation |
| People management | Not required | Technical leadership, not line management |

## Stage 4: Company research

Jordan researches the company's revenue model, funding, cash position, customer concentration, competition, and recent hiring or restructuring. Private-company financial estimates are labeled as estimates, with sources and dates.

## Stage 5: Targeted resume bullet

> Implemented Kafka consumers for distributed financial workflows and coordinated schema compatibility across four downstream teams, improving consistency of transaction updates while supporting production troubleshooting.

The bullet does not invent a percentage, claim ownership of Kafka infrastructure, or imply Jordan designed the entire platform.

## Stage 6: Improve the source of truth

After the interview, Jordan remembers a second project involving API versioning. That evidence is added to the master inventory once confirmed. It can support future applications without rewriting existing facts to fit a particular employer.
